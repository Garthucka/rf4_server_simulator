# Руководство для контрибьюторов

Спасибо за участие в `rf4_server_simulator`. Руководство распространяется на всех авторов, людей и ИИ-агентов. Отправляя Issue, Pull Request или код, вы соглашаетесь соблюдать это руководство и существующие правила открытого проекта.

## Границы проекта

Проект представляет собой одиночный серверный эмулятор. Он предназначен для технических исследований, обучения и локальной игры, а также может работать в локальной сети. Это не проект по эксплуатации частных серверов и не коммерческий сервис.

Следующее принято не будет:

- платформы пополнения реальной валюты, платежей, пожертвований, спонсорства, платных подписок или продажи токенов;
- регистрация по инвайт-кодам, продажа аккаунтов, платная активация, агенты, дистрибуция или механизмы возврата средств;
- платформы управления для создания коммерческих частных серверов, мультиарендного хостинга, централизованной эксплуатации или обхода авторизации;
- официальные игровые материалы, файлы клиента, данные повторов и другие проприетарные ресурсы без явного разрешения;
- код, крадущий учётные данные, обходящий авторизацию, удалённо управляющий системой, скрыто собирающий телеметрию или иначе непригодный для открытого распространения.

Можно вносить одиночный геймплей, использующий только внутриигровую валюту локального сохранения, возможности сетевой игры в локальной сети и обычные административные функции. При этом нельзя подключать реальные платежи или цепочки платной эксплуатации.

## Гранулярность коммитов

### Один коммит делает одно дело

- Коммит должен решать одну проблему или завершать одну неделимую небольшую функцию.
- Реализацию, необходимые тесты, миграции и документацию по одной проблеме можно держать в одном коммите.
- Не смешивайте в одном коммите форматирование, несвязанный рефакторинг, обновление зависимостей, правку текстов и другие исправления.
- Не складывайте в один большой коммит несколько несвязанных проблем.

### В одном PR по возможности один коммит

- Один PR должен решать одну чётко определённую проблему.
- В PR не более 3 коммитов, и все они должны служить одной проблеме.
- Если коммитов больше 3, сначала сожмите их или разделите локально и отправьте заново.
- Если изменения затрагивают несколько независимых проблем, разделите их на несколько PR.
- При обновлении ветки предпочитайте rebase, чтобы не тянуть в PR с функцией merge-коммиты из upstream.

## Сообщение коммита

Сообщение коммита пишется на коротком и ясном китайском языке, рекомендуется не более 30 иероглифов.

Рекомендуемые примеры (по смыслу):

```text
Исправить вылет на странице редкой рыбы
Добавить проверку ёмкости садка
Добавить миграцию срока членства
Улучшить руководство для контрибьюторов
```

Нежелательные:

```text
update
fix bug
misc changes
Изменил кое-что
```

Для сложных изменений под заголовком можно добавить текст на китайском с причиной, влиянием и способом проверки. Не используйте вводящие в заблуждение заголовки и не описывайте незавершённые изменения как исправленные.

## Правила для кода и документации

- Перед правкой прочитайте нужную реализацию, места вызова и тесты и делайте минимальные изменения.
- Комментарии и документация описывают только то, что делает функция, зачем она нужна и на что обратить внимание при использовании.
- Не записывайте историю инцидентов, личный ход расследования, построчные сравнения с эталонными реализациями, внутренние аудиторские выводы и локальные пути.
- Перед коммитом код на Go прогоняйте через `gofmt`.
- Новые функции и исправления поведения должны сопровождаться тестами.
- Перед отправкой выполните как минимум:

```text
go test ./...
go vet ./...
go build ./...
```

- Если в полном наборе тестов есть ранее существовавшие сбои, не связанные с вашим изменением, их нужно явно перечислить в PR. Нельзя утверждать, что всё прошло.
- Для изменений протокола укажите версию клиента, основание в виде реального пакета и регрессионный сценарий. Сейчас поддерживается клиент `4.0.25034`.
- Миграции базы данных должны быть повторяемыми, откатываемыми при сбое и покрывать тест обновления старой базы.
- Нельзя коммитить недействительные ресурсы, файлы-заглушки, страницы ошибок загрузки и статические ресурсы, на которые нет ссылок.
- Сетевые и фронтенд-ресурсы нужно проверить на фактическую загрузку. При использовании сторонних материалов обязательно указывайте источник и лицензию.

## Открытый код и соответствие требованиям

- Вносимое содержимое должно быть совместимо с `LICENSE` репозитория.
- При добавлении стороннего кода, изображений, шрифтов, стилей и других ресурсов сохраняйте лицензию и указание источника.
- Нельзя коммитить данные реальных игроков, сохранения, базы данных, логи, сертификаты, токены, ключи, конфигурацию и артефакты сборки.
- Нельзя коммитить файлы с абсолютными путями на вашей машине, личными аккаунтами или приватной информацией.
- Нельзя использовать официальные материалы неизвестного происхождения или без разрешения для построения интерфейса частного сервера.

### Материалы реверса и локальный справочный каталог

- **Материалы реверс-инжиниринга** (декомпиляция клиента, перехват пакетов и т. п.) по умолчанию хранятся только в локальном каталоге `ref/` (он исключён через `.gitignore`).
  - Сюда входят, в том числе: `Assembly-CSharp.dll`, `global-metadata.dat`, декомпилированный исходный код, индексы IDA и семантические индексы, артефакты `rf4_hook`, сырой hex перехваченных пакетов, данные повторов официального клиента.
- Эти материалы остаются только локально для сверки протокола. **Их нельзя коммитить**. Нельзя раскрывать содержащиеся в них сырые байты, аккаунты и пути в PR, Issue, логах и документации.
- Для ссылок на выводы по протоколу используйте уже оформленные выводы в `docs/` (например, `docs/debugging-workflow.md`, `docs/official-protocol-workshop.md`), а не сырые файлы из `ref/`.

## Требования к вкладу ИИ-агентов

ИИ-агенты соблюдают те же стандарты, что и люди, и дополнительно:

- Изменяют только файлы, связанные с текущей задачей.
- Не перезаписывают и не откатывают несвязанные изменения пользователя и других авторов.
- Не подделывают результаты тестов, сборки, проверки на реальном клиенте и ревью.
- Перечисляют в PR фактически выполненные команды, их результаты и непроверенные части.
- Не коммитят временные файлы агента, кэши, отладочные скрипты и личные данные, созданные инструментами.
- При cherry-pick или повторе чужих коммитов сохраняют информацию об исходном авторе. Для смены адреса автора нужно явное подтверждение.
- Если задача требует разбиения, сами сужают объём коммита и не объединяют большой PR ради удобства.

## Требования к PR

Описание PR должно содержать как минимум:

1. Решаемую проблему.
2. Способ реализации.
3. Команды тестов и результаты.
4. Известные риски или непроверенное.
5. Связанные Issue.

Перед слиянием PR нужно убедиться, что:

- число коммитов не больше 3;
- каждый коммит имеет одну задачу;
- нет посторонних файлов, личных данных и материалов без разрешения;
- в одиночные функции не примешаны эксплуатация частного сервера, реальные платежи, пожертвования или регистрация по инвайт-кодам;
- CI, сборка и необходимые регрессионные тесты проходят.

Спасибо каждому, кто соблюдает эти правила. Ясные, сдержанные и проверяемые коммиты ценнее, чем один коммит с большим числом изменений.
